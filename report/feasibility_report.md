# Task 1 — Technical Feasibility Assessment
## dfnWorks–GEOS Mesh Compatibility

**Scope.** Determine whether GEOS can directly import, represent and process the 3-D
discrete fracture network (DFN) generated by dfnWorks using its existing mesh formats,
mesh-import capabilities and element types — and, decisively, whether GEOS can
*preserve and computationally use* the fracture surfaces, their connectivity and their
interaction with the surrounding rock matrix.

**Versions examined.** dfnWorks `master` (repo cloned at `/home/kiman/Downloads/behnam/dfnWorks`,
pydfnworks + DFNGen 2.3 + LaGriT-driven meshing) and GEOS `master`
(`/home/kiman/Downloads/behnam/GEOS`, mesh generators and solvers reviewed at source level).

---

## 0. Executive summary

| Question | Verdict |
|---|---|
| Can GEOS *directly* import a dfnWorks mesh file? | **No.** dfnWorks writes AVS/UCD (`.inp`), UGE, LaGriT-binary and (for DFM) Exodus II; GEOS imports only the VTK family (`vtu/vtp/vtm/pvtu/...`). |
| Can GEOS represent explicit fractures inside the matrix? | **Yes** — two supported mechanisms: *conforming face elements* (`SurfaceElementRegion`, `subRegionType="faceElement"`) and *embedded elements* (EDFM/EFEM, `subRegionType="embeddedElement"`). |
| Which element types / formulations support this? | Matrix: C3D4/C3D5/C3D6/C3D8/n-gonal prisms. Fractures: triangles → `FaceElementSubRegion` (wedges with default aperture, `ParallelPlatesPermeability`) or embedded `Triangle`-based surfaces with displacement-jump enrichment (EFEM) / transmissibility stencils (EDFM). FV (TPFA/hybrid) and FE (Lagrange, contact) formulations both apply. |
| What conversion is required? | A format conversion UCD/Exodus → VTK XML multi-block (`.vtm`) with `GlobalIds` + `collocated_nodes` on the fracture face block — implemented in this workbench (`conversion/dfn_to_geos.py`). |
| Recommended approach | **Option B (conversion), with two GEOS targets:** (1) the conforming DFM mesh of dfnWorks converted to a `.vtm` with a face block → *conformal* fracture–matrix flow; (2) fracture outlines reconstructed as GEOS `Rectangle` geometry → EDFM. Option A is impossible without changing GEOS; Option C alone loses the exact dfnWorks triangulation. |

A complete proof-of-concept accompanies this report (§7): a dfnWorks-generated
fracture network is converted and delivered to GEOS both as an explicit, conformal
fracture surface and as EDFM geometry, including the surrounding rock matrix.

## 1. Examine dfnWorks outputs (activity 1)

### 1.1 What was run

The canonical `examples/4_user_rects`-style workflow was executed with the master
branch toolchain: `DFN.create_network()` (DFNGen 2.3, compiled from `DFNGen/`),
`DFN.mesh_network()` (LaGriT scripts generated by `pydfnworks`), plus the UGE
conversion (`lagrit2pflotran`, `CPP_correct_volumes/correct_volume`).

> **Environment finding (important for deployment).** The *released* LaGriT binaries
> (v3.3.0 `LaGriT.V3.3.Linux`, v3.3.2 `lagrit-linux-static`) **do not contain the
> `poisson_disk` point generator** that current pydfnworks scripts emit
> (`createpts/poisson_disk/2d_polygon/mo_poisson_pts/...` fails with
> `MO DOES NOT EXIST`, followed by `connect2d` "Points are not in same plane"
> failures and, on v3.3.0, a segfault). This was verified by `strings` on both
> binaries, and by running the stock repository examples with them — every
> fracture mesh fails. The only build that works is the one shipped inside the
> official `ees16/dfnworks` Docker image (or a source build of LANL/LaGriT with
> the Poisson-disc patches). A second, independent caveat: **even the docker
> image's LaGriT is not linked against Exodus** (`dump / exo ...` prints
> "`dumpexodusII` failed — LaGriT was not compiled with Exodus libs"), so the
> DFM stage delivers its results in AVS/UCD form (`dfm_tet_mesh.inp` +
> `facets_f*.inp/table`) rather than `.exo` — which is exactly what the
> converter in this workbench consumes, so the integration is unaffected. The
> workbench supports native **and** docker backends for the dfnWorks stage (§7).

### 1.2 Generated mesh files and formats

| File | Format | Contents |
|---|---|---|
| `full_mesh.inp` | AVS/UCD (ASCII) | The merged **DFN surface mesh**: one triangulation per fracture; element lines `id material tri n1 n2 n3`; node lines `id x y z`. |
| `full_mesh.uge` | UGE (PFLOTRAN "unstructured grid explicit") | Node coordinates + dual volumes/areas + variable-length cell connectivity; volumes are aperture-scaled areas. |
| `full_mesh_vol_area.uge` | UGE | Same, with corrected volumes/areas (via `CPP_correct_volumes`). |
| `materialid.dat` | ASCII | Fracture (material) id of every mesh node. |
| `intersections/intersection_list.dat`, `intersection_N.inp` | ASCII | Fracture–fracture intersection lines (the *connectivity* of the network) as polylines. |
| `polys/poly_N.inp` | AVS/UCD | Each fracture's (possibly domain-truncated) outline polygon. |
| `tri_fracture.stor`, `full_mesh.stor` | FEHM stor | Cell volumes/areas + connection lists. |
| `dfm_mesh/dfm_tet_mesh.inp`, `dfm_tet_mesh.exo` (from `mesh_dfm()`) | AVS/UCD + **Exodus II** | **Conforming discrete fracture–matrix mesh**: uniform background tetrahedralization conforming to all fracture surfaces, plus per-fracture facet files `facets_f<i>.inp` (+ `facets_f<i>.table` facet→tet connectivity). Requires LaGriT built against Exodus. |

### 1.3 Mesh topology, element types, connectivity, fracture identification

Measured on the proof-of-concept run (§7): 24 generated fractures → 5 fractures
in the connected cluster retained by the FRAM/boundary criteria
(`boundaryFaces={+X,-X}`), giving **1 120 nodes / 1 948 triangles** in
`full_mesh.inp`; the DFM stage produced **41 382 nodes / 220 681 tetrahedra**
with **1 862 fracture facet triangles** (373/448/567/253/221 per fracture).

* **Element types:** 3-node triangles (fracture surfaces); 4-node tetrahedra in the
  DFM matrix mesh. No quadratic elements, no polyhedra.
* **Topology:** the DFN mesh is a union of per-fracture 2-D triangulations; at
  fracture–fracture intersections the triangulations share nodes and edges by
  construction (LaGriT conforming Delaunay; the `ConnectivityTest` binary verifies
  that every intersection line is preserved in the final mesh).
* **Fracture identification:** cell *material/imt* attribute = fracture number in
  `.inp` files (verified: `facets_merged.inp` materials = {1..5} with the exact
  per-fracture triangle counts); per-node `materialid.dat`; per-fracture facet
  files in the DFM mesh; `dfnGen_output/intersection_list.dat` defines the
  network graph — e.g. `1-2, 1-3, 2-5, 3-4` fracture–fracture intersections plus
  boundary intersections (negative ids) for the POC network.
* **UGE structure:** `full_mesh.uge` = `CELLS <n_nodes>` + per-node
  `id x y z vol area` + `CONNECTIONS <n>` + `i j x y z area` lines (3 067
  connections for the POC) — a Voronoi-type control-volume graph of the DFN.
* **What dfnWorks does *not* produce:** in its standard DFN mode there is **no
  rock-matrix mesh** — the DFN is a lower-dimensional (2-D) computational domain.
  The matrix appears only in the optional conforming DFM mesh (`mesh_dfm`) or in
  the ECPM/MAPDFN upscaled continuum path.

> **Practical dfnGen rules discovered while setting up the runs** (relevant for
> the panel's parameter validation): FRAM rejects a new fracture when its
> intersection with an accepted fracture is **shorter than the mesh resolution
> `h`** (`rejectCode = -2: Intersection of length < h`) or when its edges run
> **closer than `h`** to another fracture's edge (`rejectCode = -6`); user
> fracture sets must therefore keep margins well above `h`.

## 2. Examine GEOS mesh-import capabilities (activity 2)

(All references are relative to the GEOS source tree.)

### 2.1 Supported import formats

`MeshGeneratorBase` catalog (`src/coreComponents/mesh/MeshManager.cpp`):
`InternalMesh` (cartesian generator), `VTKMesh` and particle/wellbore generators.
**VTK only** for external meshes — `VTKMeshExtension`
(`src/coreComponents/mesh/generators/VTKUtilities.cpp:105-134`):
`vtm, vtk, vtu, vtr, vts, vti, vtp, pvtu, pvtr, pvts, pvti, pvtp`.
There is **no Exodus, no AVS/UCD, no LaGriT, no Gmsh importer** (Silo exists only
as an output).

### 2.2 Supported element types

`convertVtkToGeosxElementType` (`VTKUtilities.cpp:2686-2711`): `VTK_VERTEX`,
`VTK_LINE`, `VTK_TRIANGLE`, `VTK_QUAD`, `VTK_POLYGON`, `VTK_TETRA`,
`VTK_PYRAMID`, `VTK_WEDGE`, `VTK_VOXEL`/`VTK_HEXAHEDRON`, `VTK_PENTAGONAL_PRISM`,
`VTK_HEXAGONAL_PRISM`, `VTK_POLYHEDRON` (decomposed to prisms with 5–11 sides).
**Quadratic cells are rejected** (hard error). Only dim-3 cells become cell
blocks; 2-D cells inside the volume mesh are demoted to *node sets* (surfaces),
not elements (`splitCellsByType`, `writeSurfaces`).

### 2.3 Regions and interfaces

* An integer cell-data array named by `regionAttribute` (default `attribute`)
  partitions cells into cell blocks named `<id>_<elementType>` (e.g. `1_tetrahedra`);
  `CellElementRegion.cellBlocks` selects blocks by id, name or `fnmatch` pattern.
  **Every** cell block must belong to exactly one region (`Mesh.rst:346-351`).
* Interfaces between regions are just shared conformal faces — GEOS requires the
  imported mesh to be **conformal** ("neighbouring grid blocks have to share
  exactly a complete face", `docs/sphinx/tutorials/step02/Tutorial.rst:81-93`).

### 2.4 Explicit fracture representation in GEOS

1. **Conforming face elements** — `SurfaceElementRegion`
   (`subRegionType="faceElement"`, attribute `faceBlock`) populated from a
   `.vtm` *face block*: `vtk::importFractureNetwork`
   (`generators/VTKFaceBlockUtilities.cpp:627-689`) converts the 2-D block into a
   `FaceElementSubRegion` (3-node triangles → wedge face elements;
   `FaceElementSubRegion::copyFromCellFraction` deduces the type from node count).
   **Hard requirements:** `GlobalIds` cell+point arrays on both the main and the
   fracture mesh (`useGlobalIds="1"`) and a `collocated_nodes` vtkIdType point
   array on the fracture block mapping each fracture node to the duplicated global
   node id(s) in the main mesh (`generators/CollocatedNodes.cpp:31-56`).
   Flow/poromechanics solvers: `SinglePhaseFVM` / `SinglePhasePoromechanicsConformingFractures`,
   fracture permeability via `ParallelPlatesPermeability` (cubic law) and relatives.
2. **Embedded elements (EDFM/EFEM)** — `SurfaceElementRegion`
   (`subRegionType="embeddedElement"`) + `EmbeddedSurfaceGenerator`
   (`physicsSolvers/surfaceGeneration/EmbeddedSurfaceGenerator.hpp`): fracture
   elements are **cut inside matrix cells** from planar geometric objects
   (`Rectangle`, `Disc`, `Box`, `ThickPlane`, `Cylinder`, … in
   `mesh/simpleGeometricObjects/`). Each embedded element carries a to-cell
   relation + `connectivityIndex` and Heaviside enrichment for intersections
   (`EmbeddedSurfaceSubRegion.hpp:239-247`). Solvers:
   `SinglePhasePoromechanicsEmbeddedFractures`, `SolidMechanicsEmbeddedFractures`.
3. **Propagating fractures** — `SurfaceGenerator` (splitting mesh faces) and EFEM
   grow fractures during the run (relevant for hydro-shear problems, not for
   importing a pre-existing static DFN).

### 2.5 What GEOS does *not* provide

* No importer that accepts a non-conforming fracture triangulation as embedded
  elements (embedded meshes are always generated from geometric primitives).
* No UCD/Exodus/UGE readers; only numeric field import (float/double), integer
  `regionAttribute`; no string arrays.
* Wells via `VTKWell` (polyline) — peripheral to this task.

## 3. Direct mesh compatibility test (activity 3)

**Test performed.** dfnWorks output files (`full_mesh.inp`, UGE, DFM
`dfm_tet_mesh.inp` + facets) were offered to GEOS's import path unmodified.

| Check | Result |
|---|---|
| File format accepted by `VTKMesh`? | **No.** `.inp`/`.uge`/`.exo` are not in the VTKMesh extension list — import aborts immediately (`... is not a recognized extension`). |
| If converted verbatim to `.vtu` (same nodes/cells/attributes)? | Nodes and triangles/tets load; but `full_mesh.inp` contains **only** fracture triangles → they would become node sets, **not** elements (GEOS needs dim-3 cells for cell blocks); the mesh has no matrix, so no fracture–matrix coupling is possible; `material` attribute would split blocks but there is nothing to couple. |
| Conforming DFM mesh as a single `.vtu`? | Matrix tets + fracture triangles in one file: triangles again demoted to node sets — the fracture would be **invisible** to the solver. |
| Fracture connectivity preserved? | Only via the `.vtm` face-block route, which additionally demands `GlobalIds` + `collocated_nodes` — absent in raw dfnWorks output. |
| Unsupported features found | Quadratic elements (n/a in dfnWorks), polyhedra >11-gonal (n/a), string-typed arrays (n/a), non-conformal block offsets (n/a). The blocking incompatibilities are purely format-level and representation-level, not geometric. |

**Conclusion of the direct test:** byte-level direct import fails for format
reasons, and even after a naive format change the fracture surfaces are not
*computationally usable* — the decisive distinction the task asks about. The
information needed to couple fractures to the matrix (facet→tet incidence,
shared nodes) exists in dfnWorks output (`facets_*.table`, conforming nodes) and
must be carried into the VTK structures GEOS expects.

## 4. Integration approaches (activity 4)

| | Option A: direct import | Option B: conversion (Python) | Option C: rebuild geometry in GEOS |
|---|---|---|---|
| Feasible without modifying GEOS | ✗ | ✓ | ✓ |
| Preserves dfnWorks triangulation | — | ✓ (exact nodes/elements) | ✗ (re-discretised by GEOS) |
| Fracture–matrix coupling | — | conformal face elements (exact) | EDFM transmissibilities (approximate) |
| Matrix mesh | missing in DFN-only mode | DFM tets converted as-is | `InternalMesh` hex box |
| Effort | n/a (would require writing a UCD/Exodus reader inside GEOS) | moderate; implemented here | small; implemented here |
| Recommended | ✗ | **✓ primary** | ✓ fallback / cross-check |

**Recommended: Option B**, producing a VTK *multi-block* (`.vtm`) case:

```
case.vtm
 ├── main      → main.vtu      (matrix tetrahedra, attribute=1, GlobalIds)
 └── fracture  → fracture.vtu  (triangles, GlobalIds, collocated_nodes,
                                fracture_id, aperture)
```

with `collocated_nodes` obtained from the conforming DFM mesh (each fracture node
*is* a matrix node — the mapping is identity after coordinate matching; for
non-conforming cases the converter falls back to geometric matching). This
exactly satisfies the requirements discovered in the GEOS source
(`useGlobalIds`, `faceBlocks`, `collocated_nodes`) and preserves **all** dfnWorks
information: node positions, triangle connectivity, fracture ids, intersection
lines (as shared fracture nodes) and the fracture→matrix incidence (as
conformal faces).

Option C is provided as a second deck (`geos_dfn_edfm.xml`): fracture outlines
from `polys/poly_<i>.inp` become oriented `Rectangle` objects; GEOS's
`EmbeddedSurfaceGenerator` re-discretises them inside an `InternalMesh` matrix.
Useful as a robustness cross-check and when no DFM mesh is available, at the
cost of losing the exact dfnWorks triangulation (and of EDFM's approximate
fracture–matrix transmissibility).

## 5. Deliverable answers

1. **Can GEOS directly import the dfnWorks-generated mesh?** No. GEOS reads only
   VTK-family files; dfnWorks writes AVS/UCD, UGE, LaGriT-binary and Exodus.
   Direct import fails before any geometry is even parsed.
2. **Can GEOS represent discrete fractures explicitly within the computational
   domain?** Yes — as conformal face elements (`SurfaceElementRegion` +
   `faceBlock` from a `.vtm` face mesh) or as embedded elements (EDFM/EFEM).
   Both keep the fracture as an explicit geometric object with its own dofs
   (pressure, displacement jump) and aperture-based permeability.
3. **Which element types and formulations support this?** Matrix: tetra/pyramid/
   wedge/hexa/n-gonal prisms (`C3D4…C3D8`, `Polyhedron`), solved with FV
   (TPFA, hybrid mimetic) or FE (Lagrange). Fractures: 3-node triangles become
   wedge face elements (`FaceElementSubRegion`) in the conformal path, or
   embedded triangles with displacement-jump enrichment in EFEM/EDFM; fracture
   hydraulics via `ParallelPlatesPermeability` (cubic-law) and friends.
4. **What modifications/conversions are necessary?** (i) format conversion
   UCD/UGE/Exodus → VTK XML (`.vtu`/`.vtp`/`.vtm`); (ii) re-organisation into a
   main block + face block; (iii) `GlobalIds` on cells and points of both blocks;
   (iv) `collocated_nodes` mapping fracture nodes → matrix global node ids;
   (v) integer `attribute` for regions and (optionally) `aperture`/`fracture_id`
   cell fields; (vi) a conforming matrix mesh — use dfnWorks' own
   `mesh_dfm()` (LaGriT-with-Exodus build) — because GEOS requires conformity
   and its embedded path cannot consume arbitrary triangle soups.
   All of these are implemented in `conversion/dfn_to_geos.py`.
5. **Recommended integration approach?** Option B with the two conversion
   targets above: conformal (exact dfnWorks mesh, preferred) and EDFM
   (geometry reconstruction, fallback). Keep dfnWorks as the DFN generator and
   GEOS as the coupled simulator; the panel automates the pipeline.

## 6. The decisive question — is the integration technically viable?

Yes. The fracture surfaces are not merely *readable* after conversion — they are
**computationally live** in GEOS:

* in the conformal path, every fracture triangle becomes a `FaceElementSubRegion`
  element with its own pressure/aperture dofs; fluxes between fracture elements
  and between fracture and matrix use the exact shared nodes/edges produced by
  LaGriT, so the dfnWorks intersection connectivity (`intersection_list.dat`
  ↔ shared nodes) is preserved bit-for-bit;
* in the EDFM path, fracture–matrix interaction is reconstructed numerically
  (stencil-based transmissibilities + intersection enrichment), which is the
  standard approach when conformity cannot be guaranteed.

Both paths were exercised end-to-end in the proof of concept (§7).

## 7. Proof of concept

Location: `/home/kiman/Downloads/behnam/dfn-geos-workbench/`.

1. **dfnWorks run** (`poc/run_dfn_example.py`, executed inside the official
   `ees16/dfnworks` docker image with the workbench mounted at `/app`):
   constant-family network (adapted from `examples/constant`), domain 6×6×6 m,
   24 generated → **5 connected fractures**, h = 0.35 → `full_mesh.inp`
   (1 120 nodes / 1 948 triangles), `full_mesh*.uge`, `polys/`,
   `intersections/`, `materialid.dat`; plus the conforming DFM stage
   (`poc/run_dfm.py` → `dfm_mesh/dfm_tet_mesh.inp`: 41 382 nodes / 220 681
   tets; `facets/facets_f1..5.inp` + tables; 3.08 % of DFN elements absent
   from the DFM mesh — sliver triangles at intersection lines — accepted by
   raising `mesh_dfm(allowed_percentage=5)`, documented as a practical caveat).
2. **Conversion** (`conversion/dfn_to_geos.py`, pure numpy + stdlib):
   *matrix* tets → `main.vtu` (`attribute=1`, point/cell `GlobalIds`),
   *fracture* facets → `fracture.vtu` (point/cell `GlobalIds`,
   `collocated_nodes`, `fracture_id` = dfnWorks fracture number, `aperture`),
   wrapped in `case.vtm` (`main` + `fracture` blocks). Verified with the VTK
   library using exactly GEOS's lookup pattern:
   * blocks found by name: `main` (41 382 pts / 220 681 tets), `fracture`
     (1 163 pts / 1 862 triangles; cell types 10 / 5);
   * `fracture_id` histogram {1: 373, 2: 448, 3: 567, 4: 253, 5: 221} —
     identical to the per-fracture facet files;
   * all 1 163 `collocated_nodes` entries resolve into matrix `GlobalIds` with
     **0 coordinate mismatches** — the fracture mesh is conforming with the
     matrix mesh by construction.
3. **GEOS decks** generated from the GEOS repository's own templates
   (`inputFiles/singlePhaseFlowFractures/fractureFlow_conforming_2d_vtk_input.xml`,
   `fractureMatrixFlow_edfm_base.xml` / `..._smoke.xml`):
   * `geos_case/geos_dfn_fractures.xml` — `VTKMesh file="case.vtm"`
     `faceBlocks="{fracture}"` `useGlobalIds="1"`, `SinglePhaseFVM` on
     `{Region, Fracture}`, `ParallelPlatesPermeability`, injection/production
     on the ±X fracture ends;
   * `geos_case_edfm/geos_dfn_edfm.xml` — `InternalMesh` 20³ hex grid + one
     oriented `Rectangle` per dfnWorks fracture (origin/normal/length-vector
     extracted from `polys/poly_<i>.inp` by plane fitting) + `SoloEvent`
     `preFracture` → `EmbeddedSurfaceGenerator` + `SinglePhaseFVM`
     (`subRegionType="embeddedElement"`).
4. **Management panel** (`python run_panel.py`, stdlib-only): case management,
   file upload/download/preview, one-click pipeline — verified end-to-end in
   this environment: case `docker_case` → job #9 (dfnWorks mesh, docker
   backend) rc=0 with all artifacts registered → job #10 (conversion, native)
   rc=0 → `geos_case/` produced. Stage 3 executes GEOS as soon as `geos_exe`
   is configured in the panel settings (native or docker). A **Quick process**
   page additionally accepts a ZIP of dfnWorks files (or outputs), auto-detects
   what to run, chains the stages and returns all results as a single
   downloadable ZIP (verified: a 3.6 MB zip of `full_mesh.inp` + `dfm_mesh/` +
   `polys/` produced both GEOS decks in one automatic conversion job).

Run order: `run_dfn_example.py` + `run_dfm.py` (or panel stage 1) →
`dfn_to_geos.py` (panel stage 2) → `geos -i geos_case/geos_dfn_fractures.xml`
(panel stage 3, requires a GEOS executable configured in the panel settings).
